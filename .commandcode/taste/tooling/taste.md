# Tooling Preferences

- Uses pnpm as the package manager. Confidence: 0.85
- Prefers MCP server tools over CLI or search tools. Confidence: 0.85
- When investigating library/API behavior, uses the Context7 MCP server for documentation reading and pairs it with web search rather than relying on local source alone. Confidence: 0.95
- Prefers official, industry-standard testing libraries (JUnit, Mockito, Robolectric, AndroidX Test/Espresso) over custom or reinvented test infrastructure — "don't reinvent anything." Confidence: 0.9
- Considers instrumented tests running on a real device better than JVM-only tests for hardware-dependent behavior (GPS/sensor feeds); pairs them with fast JVM unit tests for pure logic. But when device tests need manual setup (live GPS fix, skip indoors/CI) and the logic is already deterministically covered by JVM tests, prefers deleting the device tests entirely rather than keeping them. Confidence: 0.7
- Prefers deterministic, repeatable tests (e.g., injected/mock GPS fixes) over assertions that depend on real-world variability such as an actual GPS fix or movement; skeptical that real-device conditions are reliable enough for perfect tests. Confidence: 0.8
- Allows upgrading the Android Gradle Plugin (AGP) and Gradle — they are NOT blanket-pinned (reversed an earlier "don't upgrade AGP" stance) — but any toolchain bump must first be verified against F-Droid build reproducibility; accepts skipping or reverting dependency versions that would force an AGP/compileSdk bump the F-Droid pipeline can't support. Confidence: 0.9
- When doing a dependency-update pass, wants ALL outdated dependencies updated — including major version bumps (e.g., opencv 4.13 → 5.0) — not just patch/minor versions; the only hard exception is media3 (pinned to the patched fork). AGP/Gradle bumps are permitted too, as long as F-Droid reproducibility is preserved. Confidence: 0.85
- F-Droid reproducibility is a hard release constraint: before any toolchain/dependency upgrade that could affect the build, verify the F-Droid build pipeline (build-server Gradle/AGP support, deterministic APK output) won't break — explicitly framed as "just make sure fdroid reproducibility supports it so when i push app there it dont mess up." Confidence: 0.9
- Weighs major toolchain upgrades by user-visible value, not just F-Droid support: agreed to stay on stable AGP 8.13.1 and skip core-ktx/glide/okhttp updates that would force the breaking AGP 9.1+ jump, because those deps are maintenance/patch updates with "nothing user-visible" — a risky major release (R8 repackaging, built-in Kotlin) isn't worth it for zero feature gain. Confidence: 0.8
- Audits the dependency list against actual code references during size-reduction passes and wants truly unused libraries stripped from the build entirely (zero references anywhere in source, e.g., media3-session and mp4parser/isoparser deleted from the dependency block) rather than kept "just in case" — the lighter edition should carry only what it actually uses. Confidence: 0.8
- Prefers universal (all-ABI) APK builds for anything shipped/distributed so any user on any device can install it — flags ABI-specific single-architecture builds (e.g., arm64-only) as a distribution problem ("we should use the universal build so any user can install it on any device... someone has [another] device"), even though a per-device install flow auto-picks the right ABI; per-ABI-only policy is acceptable at most for internal/full-Pro tier builds, never the distributable Lite line. Confidence: 0.85
- When hunting size savings, wants dead/unused resources (drawables, files) hunted down with static-analysis tooling — "try checking using any tool are there any dead resource files or drawables or anything that are not used and we can del that as well to get space?" — rather than trusting only the release resource shrinker to strip them; tool-driven dead-resource audits are welcomed as an extra size lever. Wants this audit to go "very deep" into old/legacy references, because a years-old app can contain files that are referenced (kept alive/unshrunk) but never actually used — "go very deep and find each and everything". Confidence: 0.8
- When handed a new app-icon source image, expects the full Android-Studio-style asset matrix generated with CLI tooling (magick/cwebp): legacy `ic_launcher` + `ic_launcher_round` + adaptive-icon foreground for every density (mdpi→xxxhdpi at the standard sizes), round-mask application, adaptive-icon XMLs under `mipmap-anydpi-v26` with a background color sampled to match the art, and the set placed in the target flavor's source set (e.g., `src/lite/res`) — matching however the project's existing icons are laid out and leaving other editions' icons untouched. Explicitly sanctioned using CLI tools over Android Studio GUI: "you can use cli tools etc, make sure it works as expected like densities and shapes etc however its done like android studio follow that way." Confidence: 0.8
- When image/asset output looks wrong (e.g., a cwebp-encoded adaptive foreground that read as desaturated/"black and white"), prefers regenerating with established professional tooling over improvised or experimental approaches — works on a MacBook and explicitly pointed the agent to "the professional tool... some command line tools like magic tool or something" instead of "trying of doing it ourselves." The fix should mirror the project's already-working asset convention exactly (e.g., the beta flavor's PNG per-density + adaptive structure) rather than inventing a new format. Regenerated icons must also preserve the master art's full color end-to-end: a repeated on-device "black and white" report traced to ImageMagick compositing artwork onto a transparent `xc:none` canvas, which silently pulls the output PNG into Gray colorspace — so generation must force sRGB (resize/pad with `-colorspace sRGB` / `-background none ... -extent` instead of layering onto a transparent canvas) and each output file's colorspace/channels must be verified, since pixel-level red-count checks alone can pass while the file is actually grayscale. Confidence: 0.85
- When resizing/padding PNG assets with ImageMagick, preserves the source's alpha/transparency — the padding background must be `none`, not an opaque color, or a transparent asset comes out with a white filled background. The user flagged exactly this on a downloaded GitHub badge: "it was png, but now it has white filled color did you mess up something or what," traced to padding with `-background white`. Verify the source's channels/alpha and force transparent padding (`-background none -extent`) so transparent regions stay transparent; a grayscale/transparent asset should keep its alpha through resize. Confidence: 0.65
- Development machine is a Mac with Homebrew: when a task needs a CLI tool (ImageMagick, cwebp, aapt, etc.) that is not installed, installing it via Homebrew is the expected, sanctioned path — "you can check what is installed and if not installed then you can install it" — rather than avoiding the tool or improvising. Confidence: 0.6
