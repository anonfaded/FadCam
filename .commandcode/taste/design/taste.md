# UI/UX Preferences

- Prefers modern, iOS/macOS-style UI/UX with clean layouts. Confidence: 0.85
- Wants responsive, scalable card designs where content scales and stays within bleed areas, credit-card-style, with no excessive padding or wasted space. Confidence: 0.9
- Avoids truncation/ellipsis; prefers properly fixed layouts and tooltips over inline clutter. Confidence: 0.85
- Prefers professional UI copy (e.g., "feature" rather than "button"). Confidence: 0.8
- Avoids duplicate UX elements (e.g., duplicate sign-out buttons, duplicate "Linked" labels); consolidates them. Confidence: 0.75
- Prefers simple, non-alarming user-facing previews (e.g., preferences import): show a clean summary of what will be imported ("N settings ready to import") with key/type/value rows — no warning counts, no per-entry status colors, no "Import Anyway" gate; technical validation and type-repair happen silently behind the scenes because warnings are useless to users and only confuse them. Confidence: 0.9
- Prefers rounded-corner, material-card-shaped UI elements that match existing components (e.g., the bottom-sheet picker header/banner style), not plain rectangular banners. Confidence: 0.85
- Wants color-coded syntax highlighting in JSON/preview displays "for better looks" — keys, string values, numbers, booleans, and type chips each in a distinct color (classic JSON syntax coloring), not plain monochrome rows. Confidence: 0.9
- On dark backgrounds, prefers high-contrast dark-theme JSON syntax palettes (One Dark / Material Ocean style: soft blue keys, soft green strings, soft coral numbers, cyan booleans, light blue-gray for others) — explicitly dislikes purple, danger red, and warning yellow on dark UIs; wants "nicer" syntax-highlighting colors that don't feel alarming. Confidence: 0.9
- Scrolling inside a bottom sheet's scrollable content must not dismiss the sheet (an accidental scroll fling closing the dialog is a bug); the sheet's drag-to-dismiss should be disabled while content is scrolled and re-enabled only at the top. Confidence: 0.85
- A sheet/dialog that triggers an action must dismiss itself *before* the action runs — especially when the action recreates the activity — so it never lingers on screen after completion (e.g., the preferences preview sheet staying open after import is a bug). Confidence: 0.75
- In a single-mode variant (Lite = FadCam only), the whole multi-mode selector UI must go — remove the entire mode pill bar rather than just the unsupported segment, since a switcher with one option is meaningless. Confidence: 0.8
- When a section is excluded from a variant, the entire visible group must disappear — its title/header text and any adjacent buttons (info/edit icons) along with the content container, not just the main list — the user spotted a lingering "Mini Apps" title/header in the Lite sidebar after only the container row was hidden and reported it as an unfinished cut. Fresh evidence again when the user saw the mini-app row boxes/containers still present in the Lite settings even after the cards were hidden and demanded the empty boxes be removed too. Confidence: 0.9
- Bottom navigation chrome must adapt to the number of items it holds: when an edition has only a few tabs (e.g., Lite's 3: Records/Home/Settings), the dock should be a compact pill that wraps the buttons and floats centered — not a full-width bar stretched to the width intended for the Full edition's 6-item layout. Explicitly requested "wrap around the buttons... concisely compactly" for the 3-button Lite dock instead of keeping the old full-width bar. Confidence: 0.85
- When asked to make a UI element compact/narrow, the change is scoped to the specified dimension only: only the width shrinks — height, colors, text styling, and above all animations/transitions must stay exactly as they were before. A restyle that reads simpler or stripped-down versus the original is a regression, not success ("you have made it too much smaller like the height should be as it was before just the width... animations and etc everything and colors should be as it was before right now it got too simple"). The adapted element should mirror the existing component's visual language (dynamic dimens, icon tint behavior, selection styling) rather than inventing a plainer look. Confidence: 0.85
- When a variant needs compact/adapted bottom-nav chrome, the first preference is adapting the real Material/native component itself (the actual BottomNavigationView: WRAP_CONTENT width, bottom-center gravity, selected-only label visibility) rather than a custom parallel dock overlay — a re-implementation that silently loses the original component's visual language (exact colors, dock shadow, animated active-tab label appearing on switch) and renders as a flat dark-gray bar with every label always visible is rejected. But when the native component genuinely cannot be made to adapt (e.g., width-wrap keeps losing to the internal menu weighting), the user explicitly sanctions an *enhanced duplicate* of the dock as the fallback: "if we cannot fix that then maybe we should have a duplicate of it with our enhancement but if we can fix that existing one I guess that will be better." Such a duplicate must faithfully mirror the original's theme color, elevation/shadow, dynamic dimens, and animated selected-only labels — never plainer — and should drive the hidden real BottomNavigationView as its engine (reusing real selection logic, not forking it). The user expects real effort invested in root-causing why the native component won't adapt before conceding to the duplicate route. Confidence: 0.85
- Dock/tab animations must reproduce the full Material "shift" behavior exactly, with the stable/Full version's dock as the behavioral reference: an inactive item's icon must sit vertically centered with NO reserved label space underneath — reserving an empty gap for hidden labels reads as broken ("the icons are already above and there is empty space for the label"); only when a tab becomes active does the icon rise and the label appear beneath it. A missing/wrong shift animation is itself a defect the user requires fixing ("If that animation is missing and I need it"), and the fix should use the platform mechanism (label GONE when inactive, animateLayoutChanges on the item) rather than a hand-rolled alpha/fade approximation. Confidence: 0.9
- Prefers compact single-line layouts for footer/utility text: when small info items (app package/version/code, copyright, website link) end up on separate vertical lines, the user considers that space-wasting and wants them collapsed onto single lines — e.g., app info on one line ("pkg · Version: x (code)"), and copyright + website combined on one line left/right aligned (copyright start-aligned, link end-aligned). Wants the agent to "optimize it better" and bundle what can fit on one line rather than letting them stack. Confidence: 0.85
- Prefers a concise `V` prefix for version labels (e.g., `V 4.0.0-beta10.6 (52)`) instead of spelling out "Version:" — reads cleaner and better-looking, and keeps version display terse. Confidence: 0.7
- For footer/utility info rows, prefers a two-column arrangement that exploits horizontal space instead of stacking everything in one vertical column: left column holds the copyright lines with the website link directly beneath the year, and the right column holds the package name (line 1) and version (line 2). Explicitly requested moving the package/version to the right column where the link used to be, giving left = copyright + website and right = package + version. Confidence: 0.7
- When laying out small info/utility text, never let an atomic value (like the copyright year range or package name) split/wrap across two lines — the user explicitly dislikes a year that is half on one line and half below ("the whole year should be in the new line"), preferring each value kept intact and whole on its own line, even at the cost of compactness (e.g., package name on line 1, version on line 2). Confidence: 0.7
- When creating a new UI component that parallels an existing one (e.g., a "Get it on GitHub" badge alongside the existing App Store badge), the existing component is the design source-of-truth: match its exact dimensions, corner radius, and font hierarchy (macro brand name larger, descriptor/action text smaller), and explicitly inspect the reference image (e.g., with the vision model) to derive exact size/design values rather than inventing a look. The reproduction must be exact — the user rejects approximations and demands "perfectly like that": icon on the left with the text block filling the remaining width (no dead/empty space), and adopting the reference's own fill/tint scheme (white-filled badge with black icon/text) rather than a variant palette. Verifying the match is done by screenshotting the rendered badge and comparing it against the reference side-by-side via the vision model, iterating on the exact proportions — the user will call out a badge whose icon is too small or whose overall width/scale makes it read bigger than the reference ("this seems bigger and width while the Apple badge seems in smaller dimensions"), so the icon must scale up to fill proportionally (not a tiny mark) and the badge must not appear larger/wider than the source. Confidence: 0.9
- On dark backgrounds, a button/badge must have adequate contrast against its immediate background card — a dark badge sitting on a dark card is a contrast failure to be fixed, with icons tinted white for visibility (e.g., the GitHub badge was "very dark on the dark background," so it got a lighter fill/stroke and a white-tinted GitHub mark). Confidence: 0.8
- When the official brand asset is available, prefers using it directly (dropping the downloaded badge image straight into the layout and resource folder as a single ImageView) over continuing to hand-craft/reproduce a custom badge in code — "lets use the badge directly... use it directly instead of custom badge." The official asset replaces the custom-built reproduction entirely, even after a custom version was already refined. The user will independently supply/replace the final image asset and expect the agent to just wire it in directly rather than iterate further on custom UI — "i replaced the pic now this is what i want instead." Confidence: 0.8
- Each product line/flavour surfaces its own changelog file, fetched from that build's own repo: the Lite line (Lite free + all Lite disguises) uses one dedicated Lite CHANGELOG shared across all its flavours, distinct from the Full line's changelog — "for lite i want a new file with separate changelog, like one new file that will be used for lite and all lite flavours." Changelog content is thus per-line, not hardcoded to Full's repo. Confidence: 0.8
- The update sheet's "Visit GitHub" button must open the correct per-flavour releases page (e.g., on a Lite Pro disguise it opens `FadCam-LitePro`'s releases, not the repo root or the wrong flavour's repo) — the user flagged that it "opened github just instead of correct releases page as per flavour." The repo/URL target must be derived from the active build's own repo. Confidence: 0.8
- Update-availability UI must reliably reflect state across app restarts: the sidebar "update available" section/cards and the hamburger update badge should re-populate on reopen (and the bottom sheet auto-show on beta) rather than silently disappearing after closing and reopening the app — a missing update section or lost badge on relaunch is reported as a bug to root-cause, not expected behavior. Confidence: 0.85
