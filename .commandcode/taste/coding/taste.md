# Coding Preferences

- Never uses fake, hardcoded, or fallback data — including synthesized/fabricated sensor values or coords-only "manual" locations; show real data or an honest 0/error instead. Confidence: 0.98
- Does not leave TODOs; expects complete, working, single-solution implementations and removal of old junk. Confidence: 0.95
- Follows industry standards and best practices. Confidence: 0.85
- Explicitly demands DRY + clean architecture: no duplication of anything — shared behavior must live in one place behind interfaces (typed provider interfaces with no-op defaults for lighter variants) rather than being copied or per-call reflected; wants proper dependency injection (seams + a single composition root) for wiring shared vs. variant-specific code. Confidence: 0.9
- Avoids Supabase edge functions for live/hot-path logic to protect free-tier limits; prefers scalable non-edge-function architecture (e.g., the Redis/worker approach used for viewer tracking). Confidence: 0.9
- Treats security as non-negotiable; validates and verifies rather than assuming. Confidence: 0.85
- Maintains a zero-log privacy policy for cloud streaming: never process or store real user IP addresses (local-network private IPs are acceptable). Confidence: 0.9
- Formats timestamps consistently everywhere, matching the admin dashboard (formatted time with a tooltip showing the full timestamp). Confidence: 0.85
- Does not want sensitive information (secrets, tokens, credentials, machine-specific paths) committed to git; wants staged changes scanned and verified safe before committing. Confidence: 0.85
- Avoids hardcoding important/tunable values; keeps internal sensor/logic constants clearly separated from user-facing settings so they can't interfere. Confidence: 0.8
- Prefers efficient, low-battery/performance-impact implementations — real-time responsiveness without loading the phone. Confidence: 0.9
- Adds comprehensive diagnostic logging to make future debugging self-sufficient, but keeps it efficient and low-overhead (no log spam or per-frame logging). Confidence: 0.95
- Cares about cold-start/launch performance: flags unnecessary work done on every app launch (service spin-up, DB scans, redundant broadcasts, network fetches) and wants it optimized or deferred rather than left as a permanent launch cost. Confidence: 0.9
- Prefers fixing the root cause of an error over suppressing the log line (e.g., fixing a broken reflection call that logs an ERROR every launch instead of just downgrading the log). Confidence: 0.95
- Never logs sensitive values at full precision (GPS coordinates, PII); redacts them to coarse precision to avoid privacy leaks. Confidence: 0.95
- Wants the whole codebase swept for real IPs/PII — not just logs and test files, but also UI placeholder data, watermark preview cards (including their lat/long preview display), layout XML samples, and comments. Confidence: 0.9
- Does not want test-only hooks/constructors cluttering production code; keeps the production API surface clean and achieves testability via industry-standard frameworks (Robolectric, reflection) or extracting pure logic into testable classes. Confidence: 0.9
 Wants test files and related config cleaned up after a testing task so no old clutter accumulates — removes dead/skipped tests that silently pass (false confidence), now-unused test permissions (e.g., leftover ACCESS_MOCK_LOCATION), and unused imports; keeps the suite lean and honest. Prefers outright deletion of whole files over keeping cleaned/slimmed versions when a test is impractical to run reliably (e.g., instrumented tests needing a device + live GPS fix), especially when the logic is already covered by deterministic JVM tests. Confidence: 0.9
- Prefers defensive, type-safe reads of persisted/imported preferences — data from older versions must never crash readers (e.g., Long-vs-Int ClassCastException on imported prefs); imports should be validated and auto-repair themselves (legacy values coerced to the types current readers expect) so users are never blocked by a crash. Explicitly demands "it won't crash and will auto repair itself" for legacy/wrong pref files across edge cases. Demands the fix cover *every* reader of the prefs file (all getters swept, not just the reported crash site) so a second/third imported file can't crash elsewhere. Confidence: 0.98
- Proactively hunts down and fixes deprecated API usage in the codebase (e.g., compiler `deprecated API` warnings surfaced during builds) instead of leaving or suppressing them — explicitly demands "don't suppress deprecation, instead upgrade": the actual code must be upgraded to the replacement APIs, not silenced via @SuppressWarnings, compiler flags, or build-config workarounds (temporary -Xlint hacks to enumerate warnings must be removed after use). Keeps the code modern and warning-free, with proper replacement APIs checked against docs. Confidence: 0.95
- Treats everything inside the repo — including bundled/vendored libraries like `app/libs/AppLockLibrary` — as first-party code that belongs in cleanup scope (deprecation fixes, commit stats), correcting the agent when it defers in-repo "third-party" code as out of scope. Confidence: 0.85
- Questions whether existing workarounds and dependency upgrades still serve the app's actual use case before keeping or adopting them — e.g., asks whether the custom fMP4-seek workaround is still needed now that recordings finalize as hybrid MP4, and resists upgrades that only benefit features the app doesn't use (like chapter-metadata reading for third-party files). Prefers verifying and removing obsolete workarounds rather than keeping them out of habit. Confidence: 0.65
- Models product variants as Android product flavors sharing one source repo (`src/main` plus flavor source sets) and explicitly avoids permanent Git branches/forks for a secondary variant like Lite — they diverge and require constant merging/cherry-picking; one shared repo means fixes in `main` benefit all variants automatically. Confidence: 0.9
- When a lighter/smaller-APK variant matters, heavy features and their dependencies/resources must be physically excluded from that build (flavor-scoped deps such as `fullImplementation`/`liteImplementation`, implementation moved out of shared `main`) — not merely hidden or disabled at runtime ("don't merely hide heavy features if APK size matters"). Actively drives removal of the biggest native dependency (the ffmpeg-kit AAR) to cut size, and wants its actual consumers mapped before removal — an architecture where the recording/capture core itself has zero heavy native deps (fMP4 via the patched Media3 muxer; ffmpeg only in optional post-processing like remux/probe) makes that removal tractable. Reaffirmed when cutting size: drop whole feature families not needed in the lighter variant (e.g., Faditor, whose remux/ffprobe consumers are the ffmpeg usage) and replace ffmpeg consumers with in-repo Java tooling (mp4parser, Media3 Transformer) strictly for Lite APKs, leaving Full variants' dependencies untouched. Confidence: 0.9
- Explicitly prefers the simplest approach over complex architecture — "we need simplicity and not complexity": one shared codebase for every edition, with tiers distinguished by package-name suffixes (e.g., `.lite`, `.litepro`) plus flavor/build-config gating rather than runtime license/IAP systems, extra flavor dimensions, or per-edition forks; heavy machinery like per-flavor dependency exclusion is deferred to later phases rather than built upfront. Confidence: 0.85
- Objects to dismissing active, in-use product code/config as "legacy" — e.g., the 'pro'/'proPlus' build types belong to the current main FadCam app (actively worked on), not a deprecated path. Comments must use accurate product-line terms (Full line vs Lite line) rather than labels like "legacy" for things still in active use. Confidence: 0.8
- Prefers clear, honest, self-documenting naming of config/build fields that must not conflate distinct product-model concepts — e.g., the primary update repo a build checks (named `UPDATE_REPO`) vs. Full's secondary pro feed (`UPDATE_PRO_REPO`). A misleading name like `UPDATE_FREE_REPO` reused for a Lite Pro repo confused the user ("its so confusing now", "u messed the stable pro with lite pro") by blurring stable-pro vs lite-pro; rename fields so the name reflects real semantics, and avoid repurposing a field name for a different concept. Confidence: 0.8
- Keeps variant config structurally consistent with the primary product: each edition mirrors the same pattern (e.g., Full and Lite both use the same two-repo update structure — a primary/stable repo plus a secondary/pro repo), with only the config values (repo names, version code/name) changing per flavor, not the wiring. Rejected a variant wired differently (a Lite "empty pro feed" single-repo model) as confusing — "the normal stable and pro has their own 2 repos, and for lite we have 2 repos as well"; wants everything to use the same "normal" structure with easy namings and repo-name swaps per flavor, leaving the version-checking logic standard. Reaffirmed: this multi-feed update design is intentionally "by design" — each variant checks its stable/beta/pro feeds and the home drawer surfaces a card for whatever is available (not just one repo's notices), and Lite mirrors it against Lite repos so users see new Lite (stable), new Lite beta, and new Lite Pro cards. Confidence: 0.85
- Wants important product/architecture decisions documented as comments in the file that implements them (e.g., the Full-vs-Lite product structure matrix written right above `flavorDimensions` in `build.gradle.kts`) so the reasoning survives future sessions ("write this info so we dont forget it, maybe in this gradle file"). Confidence: 0.85
- Keeps disguise/whitelabel identity consistent across editions: a parallel variant of a disguise product must reuse the original's launcher icon, app name, and pkg-naming pattern (Lite disguises = `.lite.notes`/`.lite.calc`/`.lite.weather` mirroring the Full `notes`/`calc`/`weather`), reusing icon assets via sourceSets instead of inventing a separate branding token like "litePro" or duplicating assets. Reaffirmed when the user spotted a stray `litePro` APK and asked whether it was being built: "Lite Pro" is only an umbrella name — the actual product is three separate disguise APKs, never a single buildable variant. Confidence: 0.8
- Removes abandoned/superseded product features entirely (UI menu items, handlers, feature-interface methods, ops bodies) rather than merely hiding them with a "keep intact for later re-enable" comment — directed full deletion of the abandoned Fix Video (ffmpeg repair) feature once it was confirmed obsolete because hybrid-MP4 recordings self-heal via the patched media3 finalization; dormant-but-kept feature code is treated as dead weight, not insurance. Confidence: 0.8
- Deletes code that a superseded architecture left behind as soon as it is confirmed dead — e.g., deleting the ViewPagerAdapter once navigation is fragment-based ("we should then del the dead code of viewpager tho as we use fragment based navigation right") — the code tree must match the current architecture, and such cleanups are expected as part of ongoing plan/feature work rather than a separate chore. Confidence: 0.8
- When pursuing aggressive APK-size targets for a slim edition, full localization support is a hard, non-negotiable requirement — all translations/locales must stay exactly as they are; locale subsetting via resConfigs is off the table as a size lever even when it is the single biggest byte win and the numeric target (<10 MB) looks unreachable by feature cuts alone ("I don't want to remove all the translations, I want all the localizations to be as it is"). Size solutions must instead come from feature exclusions and asset/image strategy — never from dropping UI languages; Android App Bundle (AAB) split delivery was explicitly rejected as a substitute, so the single APK itself must get under 10 MB. Confidence: 0.9
- Variant cuts must strip the variant's manifest and image assets along with the code: permissions/services of excluded features (e.g., screen-recording permissions) go out of the Lite manifest, and heavy drawables kept alive only by still-compiled excluded code (remote server-room backgrounds, forensics doodles, Lab flags) are freed by cutting that referencing code — the user rejects shipping resources for features a variant doesn't have ("why are you using the images still? ... we should exclude them, right?"). Reiterated after reaching a size milestone: asks that drawables/images not used in the Lite APK not be included at all ("cant we make it also to not have what we dont use ... the image etc that are not used in lite apk?"). Confidence: 0.9
- During aggressive size-reduction of a slim variant, treats core camera-recording capabilities as non-negotiable "basic features" that must stay in every edition — explicitly protects dual-cam recording from removal ("do not remove the dual cam recording because it is a basic feature") and keeps torch tools in Lite, reserving feature exclusion for genuinely unused/exotic features (remote streaming, miniapps/QR scanner). Confidence: 0.8
- Wear OS / watch support is a hard requirement for the Lite edition too — watch-related code (activities, manifest entries, splash routing) must stay in shared main and never be moved to a Full-only source set when partitioning variants ("don't remove the watch OS related code because this App light version I want to be usable on watches as well"). Only the watch's remote/streaming page may be cut from Lite; the watch app itself keeps camera/records/settings pages. Confidence: 0.95
- Treats nav/menu layout as variant-dependent: editions may reorder or hide menu items (Lite's bottom bar is Records-Home-Settings, with Remote/Faditor/Lab gone), so any wiring that assumed fixed positions breaks. Swipe navigation must follow the live visible menu order (never internal fragment positions 0-5, which landed on hidden tabs), and behaviors bound to a nav item (e.g., long-press Home opening the icon picker) must locate that item by its menu id rather than assuming a child index — an index-0 assumption made long-pressing Records open the Home icon bottom sheet in Lite. Resolve nav targets and bindings from the live menu by item id/visible order. Gesture/tab-swipe exclusion logic must ALSO be scoped per tab: a horizontally-scrollable list should only swallow an in-list horizontal swipe on the tab that actually owns that interactive surface (e.g., Home's reorderable quick-actions/mode pill); on other tabs (e.g., Records body pager) the list must NOT block an edge swipe that switches tabs — applying a Home-only exclusion globally left the Records-body swipe dead while the header row still worked. Confidence: 0.85

When a shared container keeps multiple fragments alive (ViewPager/backstack), user-facing toasts and effects must be gated to the fragment that is actually visible and not hidden — a background/hidden Home fragment firing "Preview could not start. Try long-press again." while the user is on the Records tab was reported as a bug; gate such feedback with `isVisible() && !isHidden()`. Confidence: 0.7
- User-facing capabilities that stable FadCam offers must stay at full parity in the Lite edition unless the user explicitly approves removing that specific feature — e.g., the complete launcher-alias/custom app-icon set must remain in Lite so users can change app icons exactly like stable ("I also don't want them removed because I want the user to be able to change the App icons like the normal Fadcam stable version icons"), accepting the APK-size cost of keeping them. Confidence: 0.85
- When refactoring, must not silently remove, inline, or drop existing constants/declarations that were present — the user flags a removed line ("before we had this line that you removed and never added so did this break something or are u missing it") and expects the agent to preserve or restore active identifiers and confirm nothing is broken rather than quietly rewriting them away. Confirmed by the user clarifying the update logic was intentional — "i mean the old logic was by design if u removed that" — so designed behavior must not be reverted or simplified away as if it were accidental. Confidence: 0.75
- Prefers content files (e.g., changelogs) to carry embedded format-guideline comments at the top — like the main `CHANGELOG.md` — so the expected format is self-documenting and every edition's file is maintained in the same consistent format ("add those comments like the main ones so we know format and follow that format too"). Create new per-edition files with the same header comments, not bare content. Confidence: 0.7
