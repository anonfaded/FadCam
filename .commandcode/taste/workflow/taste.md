# Workflow Preferences

- Never scp/rsync files; does all work locally and the user pushes to GitHub, then the deploy script handles the rest (the env-file scp is an exception that should remain). Confidence: 0.9
- Never edits the nested fadcam repo; always edits the main FadCam repo, and the user handles pull/push. Confidence: 0.9
- Owns sibling repos adjacent to the main project (e.g., the media3-patched fork, one folder back from FadCam) and expects them to be edited directly when a fix spans them — they are the user's own repos, not read-only third-party code. Confidence: 0.9
- Asks before making structural changes instead of silently adding templates or TODOs. Confidence: 0.8
- Documents system architecture and usage semantics in markdown files for later reference and Q&A, based on verified facts rather than assumptions. Confidence: 0.85
- When deferring a dependency upgrade/migration (e.g., media3), wants a repo-root markdown doc capturing the decision rationale ("stay pinned for now"), the current verified state, what newer versions offer, a migration checklist, and open questions — but explicitly does NOT want speculative research done at deferral time; the doc should note that fresh research happens when the migration actually starts. Confidence: 0.85
- Defers upgrade decisions on a case-by-case basis rather than a blanket rule: media3 stays pinned to the patched fork, but OpenCV gets a major-version bump (4.13 → 5.0) with the API migration done properly; the blocking factor for each dependency is whether its toolchain requirement would break the F-Droid build. Confidence: 0.85
- Reviews staged git changes before committing and wants guidance on whether files should be committed or gitignored rather than committing blindly. Confidence: 0.9
- Prefers deleting useless/junk files that are not related to the app or context, keeping the repo focused on relevant content only. Confidence: 0.9
- When asked to clean up clutter after a task, wants only throwaway junk removed (e.g., temporary Probe*.java debug files). Keeps the unit-testing infrastructure (Gradle test config, Robolectric deps, testOptions) intact for future tests, but considers one-off verification test files written during a task throwaway once they've been run and passed — "clean them, del them, they tested already" — and will call out the agent for re-creating already-verified test files. Over-deletion of infrastructure is also called out and must be restored. Confidence: 0.9
- Considers `git commit` (and similar git operations) a "dangerous command" and avoids running it themselves; prefers the agent to execute commits and other risky git steps on request. Confidence: 0.8
- Considers commands that alter phone/device state dangerous and never wants the app uninstalled — including as a side effect of instrumented-test runs (Gradle's connectedAndroidTest uninstalls the debug app afterward and wipes its data, which caused real data loss). Prefers test execution methods that leave the app installed (adb install -r + am instrument) over the auto-uninstalling Gradle task. Confidence: 0.95
- Never adds `Co-authored-by` or other AI attribution trailers to git commit messages. Confidence: 0.95
- Prefers deep, exhaustive root-cause analysis over quick fixes: dig into the source, enumerate all possible root causes and edge cases (crash, kill, stop, restart, permission revoke, etc.), and produce a comprehensive todo list so the result is robust rather than buggy. Confidence: 0.95
- When auditing logs/performance, wants a careful triage that separates OS/system chatter (not fixable) from app-owned issues and library-owned spam, finds root causes instead of just silencing logs, and only removes logs that add no diagnostic value while keeping the useful summary lines. Explicitly considers status/context logs like the update-check current-version log "important to know" — will call out and demand restoration if a useful log is removed (only junk should go). Confidence: 0.95
- Is cautious about editing core startup/lifecycle code (crash-recovery, service spin-up) during a log audit; wants such risky changes proposed and discussed as a separate focused task rather than rushed in. Confidence: 0.8
- Wants log/source files read fully to the end before diagnosing, not skimmed. Confidence: 0.85
- When given a user-reported bug or clue, verifies it against the actual code first — is it real, and did prior fixes already cover it — and traces the exact scenario end-to-end before declaring it solved or not. Confidence: 0.85
- Wants unit tests written and run to verify that fixes hold up in edge cases (e.g., watermark/speed logic), not just a compile/build check. Confidence: 0.9
- After building, expects the agent to install the app on the connected device (gradle install / adb) and verify it's actually there (package + versionName) before calling the work done — "u need to install app". The user checks that the latest build was installed so they can manually test it on their device ("also did u install the apk now so i can test it??") and treats that install as part of delivering the milestone. Confidence: 0.9
- After building and installing multiple APK variants for manual verification, wants the agent to concisely describe how to test each APK and the expected behavior (e.g., which update card / version to expect) so they can verify each on the phone — "concisely tell me steps to test each apk and expected behavior." Confidence: 0.75
- Wants plan claims verified against actual built artifacts, not just green builds: inspect the APK itself (dex contents, native-lib presence, sizes) and use command-line tools to confirm what the plan promised actually happened ("check everything by checking the APK... so we can make sure that we actually are doing what we are having in the plan"); check whether needed tools are installed and install missing ones rather than assuming. Treats the final release-APK size of every affected edition (Full and Lite alike) as part of completion — explicitly reminds the agent to "check the final size of releases of lite version too," with the slim edition driven to be "very minimal." Confidence: 0.9
When a blocking bug needs fixing, prefers implementing a diagnostic/preview feature first so the problem becomes visible and testable in-app (e.g., an import-preview UI that opens the buggy pref file and shows exactly what's malformed), and defers the actual fix until they approve after testing. Confidence: 0.85

- When working in fast/unattended ("yolo") mode, never runs dangerous or destructive commands without asking first — expects the agent to use only safe, non-destructive work commands and to check before anything risky (e.g., git operations, app uninstall, device-state changes). Confidence: 0.95

- After a large refactor or API-upgrade pass, wants a complete regression audit before sign-off: verify every newly introduced API call is version-guarded for minSdk/old-phone compatibility, confirm nothing regressed anywhere, and confirm the app still builds and runs (installed + launched) before declaring completion. Confidence: 0.85
- For layout/clearance fixes on a shared screen, prefers the simple static root-cause fix (e.g., replacing a stale hardcoded `layout_marginBottom="72dp"` in the landscape layout with the shared dimen) over clever runtime geometry correction — an `OnLayoutChangeListener` that measured the nav container and re-padded Home content to it produced a bogus multi-thousand-pixel offset and blanked the entire landscape UI ("Landscape mode, everything is disappeared, and the whole UI screen is broken. You have made it worse") and had to be fully reverted. Any dock/padding change in shared code must be verified on-device in BOTH portrait and landscape (and ideally side-by-side vs the reference edition) before being declared fixed. Confidence: 0.75
- A separate GitHub repo is acceptable for distribution/documentation only (README, screenshots, release/download links, and the auto-update feed) — never as a source fork; actual source stays in the main repo so it never diverges. This extends to release/versioning management across shared-codebase variants: each *product line* keeps its own versionCode/versionName track and its auto-update check points at its own dedicated release repo, but all variants *within the same line* share a single version track and one release repo — per-flavor versioning for members of the same line is explicitly unwanted as "confusing." Every variant checks its **primary/stable repo AND a secondary/pro repo** — two repos, mirroring the primary product's structure — with only the repo names and the version track differing per line, and the update-check logic itself staying standard ("normal"). Known tracks: Full = `FadCam` + `FadCamPro`; Lite Free and all Lite Pro disguises (liteNotes/liteCalc/liteWeather) each check `FadCam-Lite` (primary) + `FadCam-LitePro` (secondary). Lite Free owns `100/1.0.0`; all Lite Pro disguises share one track `200/1.0.0`. The user rejected a Lite wired differently (a single-repo/"empty pro feed" model) as confusing — variants must keep the same structural pattern as the primary product and only swap values (repo names, version code/name), not the wiring. Existing, already-working track config (e.g., Full/Full-Pro) is left untouched ("for pro we already have all setup") rather than re-engineered, while fixes keep flowing from the shared source. The version/repo values themselves should be declared once as a single source of truth — named `val` variables at the top of the flavor block (e.g., `liteProVersionCode`, `liteProVersionName`, `liteProRepo`), so one edit propagates to every same-line variant instead of duplicating literals per flavor. The user explicitly wants "one place for edit only and that applies to all" and flags scattered/duplicated per-flavor strings as confusing. Confidence: 0.9
- Before committing to a product/architecture plan (e.g., a Lite variant), wants a current-state survey/gap analysis of what already exists in the repo ("tell me what we already have so we can make informed plan") so plans build on existing work rather than assuming greenfield. Confidence: 0.65
- When executing a multi-step build/feature effort, wants a living, concise markdown plan file with checkable checklist items kept in the repo and updated as each step completes ("make a markdown concise plan file with checkable items and keep updating it with things we do") — enabling progress tracking toward a time-boxed goal like shipping in one day. Confidence: 0.9
- Stages edition/variant work so the first milestone is an installable-as-is build on the connected device (no deep refactor or dependency surgery before it can run), then iterates from there — and treats "we will not break system" (existing variants, already-installed apps, shared-code fixes) as a hard constraint throughout. Reiterated explicitly when scoping risky work to one variant: size/dependency changes for Lite must be "strictly for lite apks only and not destroy other fadcam versions at all — we must be very careful." Reaffirmed yet again when delegating the risky Lite refactor: "just continue and complete tho, be sure not to break anything." Confidence: 0.95
- Delegates technical execution decisions once direction is set: when asked whether to push through a multi-step refactor or pause for review and the user answers "idk just continue and complete tho," they want the agent to proceed autonomously through the full remaining scope to completion — making reasonable implementation judgment calls (source-set moves, reflection seams, keep rules, build verification) without further checkpoint questions — with the no-breakage constraint on existing variants as the only hard requirement. Reaffirmed when the user said "ok continue please and complete it all," and again answered "yes, please continue so we can then continue ahead" when asked to proceed with the next cut. Confidence: 0.85
- Develops against debug builds only during the active fix-and-complete phase — release APKs must not be produced repeatedly while the app is still being worked on. Explicitly scolded the agent for assembling releases mid-development ("Please stop making the release App again and again. We are first fixing the App and making it complete — we need to be fast in development"); release assemble/signing is deferred until the app is actually complete. Confidence: 0.9
- Sets hard numeric size targets for slim variants and keeps pushing past earlier wins — e.g., Lite "should be under 10 MB" after already dropping 91.9 → 16.5 MB — and expects the agent to check and report what else can be cut, grounded in real byte-level measurement (compressed dex vs resources.arsc/assets/images breakdown), proposing the next levers rather than declaring the job done at the current size. Confidence: 0.85
- Grants a "continue" only conditionally on the work serving the active goal (e.g., authorizing the next cut with "Continue if it will help us reduce the size of the App"). When asked to proceed, prioritize remaining steps by measured benefit toward that goal and be willing to re-scope or stop when remaining work projects little gain or carries risk out of proportion to it — reporting the tradeoff rather than pushing ahead for its own sake. Confidence: 0.6
- When the user approves a cut list toward a size goal, expects every item on it to actually be executed rather than deferred to a later session or recommended away — the user notices unfinished approved removals and calls them out ("I told you to remove the mini apps and the remote feature... why still you didn't remove your things?"), re-affirming the approved scope along with explicit exclusions. Confidence: 0.75
- Before declaring a task complete, must self-verify across every surface the change touches instead of patching only the reported spot: all visible parts of a UI (a removed section includes its title/header and adjacent buttons, not just the content container), every variant/edition, leftover code in the staged/working diff that belongs to a moved-out feature (user: "in the get staged changes there are still files with the watch related code so please grab them out and understand and fix if there is something not correct"), and all related behaviors. Failing this draws an explicit rebuke — "you need to properly check overall and edge cases and here and there yourself instead of just doing the little bit work and leaving the other part... self-verify and self-correct yourself and check everything before telling me that you are done" — so "done" is only claimable after a full sweep, not after the first green build. Confidence: 0.95
- Maintains a running backlog of every change requested across turns and expects all of it to be completed in the same effort — will open with "what about the other things I told you? You have still not done that" when an earlier request (e.g., the compact Lite dock) went unaddressed while later items were handled. Before replying, sweep the full list of outstanding requests from prior messages, not just the current one. Confidence: 0.8
- Prefers to centralize shared content/asset files (e.g., changelogs) in the MAIN repo with distinct per-edition file names (Full = `CHANGELOG.md`, Lite & all Lite flavors = `CHANGELOG_LITE.md`) so everything is "managed from one place correctly" — rather than fetching each flavor's content from its own dedicated product repo. Explicitly rejected an earlier design that pulled each flavor's changelog from its own repo; a single repo with one named file per edition is the single source of truth, and the per-edition file name is chosen via the edition flag (e.g., `LITE_EDITION`). Confidence: 0.85
- During iterative development of a single variant, builds/installs only that variant under test (e.g., `:app:installLiteDebug`) and does not rebuild all four variants each time — "rebuilding Lite debug only per your workflow"; the full multi-variant rebuild is reserved for a later completion pass rather than every iteration. Confidence: 0.75
- Source design files (e.g., PSDs/PNGs in the `design-assets/` folder) are master artwork that must never be deleted — they are the input used to regenerate derived assets such as per-density app icons ("dont del it but you need to use some tooling on this to make it have its all resolution variations like how other icons have"). Deleting them would forfeit the ability to regenerate resolution variants later. Confidence: 0.7

The user flagged that they were on the debug build ("I am using the debug version which is using the debug icon... let's build the release and install it so I can check that it is having the latest icon or not") and expects the icon to be wired end-to-end and confirmed on-device from the correct artifact; this is the accepted exception to debug-only cycles. When the user says "install" in this context, they mean build AND install the release APK of the actual product app (FadCam Lite) — not a debug/beta stand-in — and will correct the agent with "I mean build and install the release version on my App of Fadcam Lite" if a release install was offered but not carried out. Wants this release workflow documented as an in-file comment in `app/build.gradle.kts`. Confidence: 0.7

- When asked to change a value/content, makes the smallest targeted edit that matches the exact request and does NOT rework the surrounding layout/structure — changing the About footer strings was requested, and the agent reworking the footer layout and breaking it drew "i just said to update outdated strings, not break it." Scope the change to the requested target; preserve the existing design and only swap the intended content. Confidence: 0.8

Reuse the established, already-validated fix before re-deriving one. Confidence: 0.75
- When chasing a hard-to-reproduce bug (especially one that only manifests on a specific device/encoder), follows an instrument-then-fix workflow: adds targeted debug logging to BOTH the app and the locally-patched library (media3), re-tests on the affected device to gather fresh logs that existing ones didn't capture, and does NOT change behavior/code until the root cause is confirmed by those logs — "we must not code, until we find legit root causes, and we need to add debug loggings too so it can be again tested." Confidence: 0.9

Confidence: 0.8
