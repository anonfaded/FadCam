# Communication Preferences

- Prefers "caveman skill" in ultra mode for ultra-concise, token-saving responses in chat. Confidence: 0.95
- Wants technical explanations to be concise and use real-world analogies, progressing from ELI5 up to expert level so concepts are learned permanently. Asks follow-up clarifying questions ("what u mean by diff sizes in output") when a concept is only mentioned in passing — so concepts should be grounded in concrete before/after examples. Confidence: 0.93
- When explaining library/dependency upgrades, explicitly separates the library-version axis (code ships inside the APK, so a fix reaches ALL users on any Android version once they update the app) from the Android-OS-version axis (per-device, tied to phone age) — the user conflates the two and needs the old-phone/minSdk impact stated explicitly (e.g., "the seeking fix ships in the APK, so it works even on Android 7; minSdk impact is zero"). Confidence: 0.75
- Prefers to always be very concise in responses (explicitly asks "tell me very concisely" when asking follow-up questions). Confidence: 0.97
- Prefers honest, non-overpromising answers — no false "always works, zero bugs" guarantees; values verified, evidence-backed claims. Confidence: 0.85
- Applies the privacy/redaction policy to test code too — no real-world PII (real GPS coordinates from user logs, IPs, credentials) in test files; uses clearly synthetic values instead. Confidence: 0.9
- Wants to see actual test results/output as proof when tests pass or a fix works — so they can verify what manual testing would look like — not just summary claims of success. Confidence: 0.8
- Wants commit messages to quantify the scope of an upgrade/cleanup (e.g., explicitly asked "how many deprecated apis did we upgrade" — expects counts of APIs modernized, files changed, insertions/deletions) so the commit itself documents its impact. Confidence: 0.85
- When asking about the effects of completed code changes, wants to know the user-visible impact first (what they'll actually see/experience — e.g., whether recording behavior changes) and whether it's just internal modernization vs. a behavior change. Confidence: 0.7
- Conflates related-but-distinct technical concepts when weighing feature/upgrade decisions — e.g., app-side bookmarks (user-created points the app stores) vs. library-side chapter metadata (markers baked into third-party files), and the recording-time fMP4 format vs. the finalized hybrid MP4 — and needs the agent to explicitly untangle what belongs to the app's own data/pipeline vs. what the library offers for third-party files before deciding what's worth doing. Confidence: 0.8
- When positioning features with privacy/security implications (e.g., app-disguise/identity switching), distinguishes casual inconspicuousness from real protection — disguise is "not true security or forensic hiding" and must not be marketed as a guarantee of hiding from the OS or forensic analysis. Confidence: 0.7
- When the user expresses confusion about whether the current implementation matches their product model (e.g., "is it already like this or not bcz i m confused"), answers with a direct yes/no plus proof from the actual config (grep of gradle/source, listing of outputs) — distinguishing stale build leftovers from live state — and treats the user's confirmation ("if yes then ok continue") as the gate before moving on. The user monitors build-output APK names and flags stray artifacts as potential regressions. Confidence: 0.6
- Once the user states a fixed requirement (e.g., "APK under 10 MB", "no AAB"), treats it as settled and reacts with "we don't need the AAB delivery. Just do what I said" when the agent pitches a different approach — execute the stated goal directly and don't re-litigate decided constraints. Confidence: 0.85
- Wants the agent to conserve tokens: respond concisely and compactly, and avoid taking device screenshots (ss) / screenshot-and-inspect checks when they aren't needed — "we should save tokens so dont always take ss and check when not needed and also respond concisely and compactly and save tokens ok." Treats unnecessary captures/verification as token waste; does a capture only when it actually adds signal. Confidence: 0.9
- Dislikes invented/abstract binary labels in explanations that don't match the product model — objects to "primary/secondary" framing with "what u mean primary and secondary? each apk cheks its own repo just, why u said first and secondary." Prefers describing each item concretely and plainly per what it actually does, and dropping the abstraction when the user questions it. Confidence: 0.7
- When unsure about the intent behind existing code/logic (especially logic the user deliberately designed), asks or corrects the user FIRST rather than unilaterally altering the code based on an assumption — unsolicited logic changes are seen as breaking intentional behavior and must be reverted. Explicitly: "instead of correcting me u broke the logic so revert this" and "when unsure u should ask or correct me instead of altering code for it." This also applies when the user poses a hypothesis to be validated ("correct me if I am wrong, to test should I release v1.0.0 on lite pro?"): answer with a direct confirm/correct of their mental model and make NO code change — the agent jumped to modifying the hasPro logic and got "no again u broke it, i said correct me if i am wrong," then had to revert. Confidence: 0.9
- Wants exact APK/ABI naming when identifying which build to share — flags it when an agent calls a beta "universal" that is actually the arm64-v8a build, and distinguishes per-ABI (arm64-v8a) from universal (all-ABI) artifacts rather than overstating which one was produced. Confidence: 0.7
